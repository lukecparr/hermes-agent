## Retention

Private media recovery scans at authority startup and idle housekeeping using the existing media max-age. It removes only old private owners not referenced by live admissions or any retained transcript; referenced files remain as long as their transcripts, and malformed/unsafe entries stop the sweep and require operator review. Staging cleanup runs on new attachment submissions under the fence and a size cap; payload-bearing unreadable manifests are deliberately retained and require review. Do not delete uncertain data or touch the unrelated shared native cache.

For sender rows, after 90 days an operator may run `python scripts/prune_piper_outbox.py --database <existing-state.db> --confirm`; each invocation removes at most 100 acknowledged rows, never pending/leased/blocked or old rows lacking a terminal timestamp. SB can prune sent delivery rows in bounded batches after 90 days via its separately reviewed `PIPER_PUSH_RETENTION=1` dispatch option or `PIPER_PUSH_RETENTION=1 pnpm exec tsx scripts/prune-piper-deliveries.ts --confirm`. Receiver event tombstones and phone seen IDs are intentionally retained indefinitely; monitor growth. Keep tombstones consistent across backup/restore to prevent replays. Never run maintenance without an approved backup and explicit authority.

## Rollback (only after separate approval)

- Push: first pause the SB dispatch scheduler and stop the sender worker so a disabled receiver cannot turn queued events into blocked 404s. Set `PIPER_PUSH_DISPATCH` and `PIPER_PUSH_RECEIVER` off, remove the optional writer configuration and plugin enablement, then perform any required approved service restarts. Leave queued outbox/delivery data and tombstones intact; do not blindly replay stale pushes when resuming. If restoring an older SB backup, stop all senders and reconcile event tombstones against the gateway outbox before resuming.
- Attachments: remove `HERMES_SHARED_THREAD_MEDIA_V1=1` from the gateway service environment and restart the gateway under the approved procedure; verify capability false and that file admission returns 503. Leave stored private files and existing chat data in place.
- Code: stop the affected service under the approved procedure, restore the recorded previous immutable gateway/plugin and SB image/checkout plus prior protected configuration, then restart in dependency order and verify normal chat. Preserve pre-existing local changes. The four SB migrations are additive; do not run destructive down migrations or restore an old database over new user activity. Database point-in-time restore is a separate data-loss decision requiring explicit approval.
